# 首页棋盘仪表盘 UX 优化设计

**日期:** 2026-05-19
**状态:** 已确认
**选择方案:** B. 棋盘居中仪表盘

---

## 1. 背景

当前五子棋界面采用两阶段流程：用户先进入模式选择页，选择双人或 AI 难度后才看到棋盘。这个流程清晰，但首页缺少游戏主体，用户打开应用时不能立即感知“正在进入一张棋桌”。

本次优化将首页与棋盘合并：首屏直接展示棋盘，模式选择、回合状态和重新开始等操作围绕棋盘组织。视觉上继续沿用深色檀木棋桌主题，但减少空屏感，让体验更像一个精致、专注的对弈仪表盘。

## 2. 目标

- 首页打开后立即展示棋盘，不再出现独立模式选择页。
- 模式选择保留在首屏，用户先在“双人”和“AI 对战”之间切换；进入 AI 对战后再选择简单、中等、困难，默认难度为中等。
- 棋盘保持视觉主角，状态与操作靠近棋盘但不遮挡棋盘。
- 移动端保持棋盘可用，顶部工具条允许换行，按钮不挤压棋盘。
- 保留现有游戏逻辑、AI 行为、落子动画、最后落子提示和胜利高亮。

## 3. 非目标

- 不新增排行榜、计时器、悔棋、保存对局或历史记录。
- 不改动 AI 算法和胜负判断规则。
- 不引入新的 UI 框架或状态管理库。
- 不将棋盘改成 Canvas；继续使用现有 React 组件和 CSS 网格。

## 4. 市场标准参照

本方案参考主流 App、小游戏和仪表盘的通用布局规律，不照搬大型设计系统的视觉外壳，而是提取适合五子棋的结构原则。

### 4.1 标准设计原则

- **主内容优先:** Apple HIG 强调布局应在打开 App 的瞬间帮助用户进入内容，控制与内容之间要保持熟悉关系。对应到五子棋，棋盘必须是首屏主体，模式和状态只作为围绕棋盘的 HUD。
- **响应式栅格:** Material Design 的响应式布局强调按断点重排，并用一致的边距、间距和网格保持稳定。对应到本项目，桌面端横向展开控制区，移动端将控制区堆叠，不让棋盘横向溢出。
- **分段选择:** 市面上常见模式切换使用 segmented control / toggle group，而不是散落的普通按钮。对应到本项目，`双人 / AI 对战` 是第一组，`简单 / 中等 / 困难` 是第二组，两个组要视觉上相关但层级不同。
- **即时状态反馈:** 控件交互后要立即反映状态。选择 AI 对战后，模式徽标、难度选中态、棋盘重置都要同步出现。
- **降低认知负担:** 仪表盘类界面应减少无关信息，重要状态放在用户视线自然路径上。本项目只展示“当前模式、当前回合、胜负、重开”，不增加说明文案。

### 4.2 对标页面布局

市面上成熟棋类/休闲游戏通常采用三段式结构：

1. **顶部控制带:** 标题、模式、设置入口或轻量控制。
2. **中央游戏区:** 棋盘、牌桌、地图、画布等主交互对象。
3. **底部状态带:** 当前回合、分数、结果、继续/重开按钮。

本项目采用同样结构，但控制数量更少：

```text
┌────────────────────────────────────────────────────────┐
│ 五子棋       [双人] [AI 对战]    AI 难度 [简单][中等][困难] │
├────────────────────────────────────────────────────────┤
│                                                        │
│                     15 x 15 棋盘                       │
│                                                        │
├────────────────────────────────────────────────────────┤
│                 [双人]   黑棋回合   [重新开始]           │
└────────────────────────────────────────────────────────┘
```

### 4.3 响应式断点

- **Compact `< 600px`:** 单列布局。标题居中，模式组和难度组各自换行，棋盘宽度使用 `clamp()` 控制，状态区在棋盘下方换行显示。
- **Medium `600px - 959px`:** 单列但更宽松。标题与控制区可同一行，也允许控制区换行；棋盘保持居中。
- **Expanded `>= 960px`:** 顶部左右布局。标题在左，控制区在右；棋盘居中，底部状态条保持一行。

### 4.4 可点区域与密度

- 模式和难度按钮最小高度不低于 `44px`，移动端优先保证可点面积。
- 按钮使用 8px 以内圆角，保持桌面工具感，不使用夸张胶囊形。
- 控制组之间使用 12px 到 16px 间距，同组按钮使用 8px 间距。
- 状态条固定最小高度，避免“AI 思考 / 胜利 / 重新开始”出现时推动棋盘跳动。

## 5. 用户体验设计

### 5.1 页面结构

采用居中仪表盘结构：

1. 顶部区域展示标题、当前模式标签和模式切换控件。
2. 中央区域展示棋盘，棋盘始终是最大、最稳定的视觉元素。
3. 底部区域展示回合状态、AI 思考状态、胜负结果和重新开始按钮。

桌面端布局：

```text
┌────────────────────────────────────────────┐
│ 五子棋        [双人] [AI 对战]  难度: [简单] [中等] [困难] │
├────────────────────────────────────────────┤
│                                            │
│                  15 x 15 棋盘              │
│                                            │
├────────────────────────────────────────────┤
│        黑棋回合 / AI 正在思考 / 白棋获胜     │
│                 [重新开始]                 │
└────────────────────────────────────────────┘
```

移动端布局：

```text
┌────────────────────┐
│       五子棋        │
│ [双人] [AI 对战]    │
│ 难度 [简单] [中等]  │
│      [困难]         │
├────────────────────┤
│      自适应棋盘      │
├────────────────────┤
│       状态与操作      │
└────────────────────┘
```

### 5.2 模式切换行为

模式按钮常驻顶部，分为两层：第一层选择“双人”或“AI 对战”，第二层选择 AI 难度。会改变对局类型的操作立即开始新局：

- 选择“双人”时，设置模式为 `pvp`，重置棋盘。
- 选择“AI 对战”时，设置模式为 `ai`，沿用当前 `aiDifficulty`；初始默认难度为 `medium`。
- 在 AI 对战下选择“简单 / 中等 / 困难”时，设置对应 `aiDifficulty`，并开始一局新的 AI 对战。
- 当前模式按钮和当前难度按钮呈选中状态，其他按钮保持次级状态。
- 默认进入页面时直接以“双人”开始，AI 难度预设为“中等”，棋盘可立即落子。

这个行为比“先选择再展示棋盘”更短，也避免用户在模式页和棋盘页之间来回切换。

### 5.3 状态反馈

状态区放在棋盘下方并保持固定位置，避免内容变化造成棋盘跳动：

- 正常回合：显示“黑棋回合”“白棋回合”或“白棋 (AI) 回合”。
- AI 思考：显示“AI 正在思考...”并使用轻微呼吸动效。
- 胜利：显示“黑棋获胜!”或“白棋获胜!”并突出金色反馈。
- 胜利后显示“重新开始”按钮；游戏进行中不显示该按钮。

### 5.4 视觉方向

采用“精致棋桌仪表盘”方向，而不是营销式首页：

- 主题延续深色檀木、米白文字、金色强调。
- 顶部工具条采用低对比背景，不抢棋盘注意力。
- 棋盘保持木纹、阴影和棋子立体感。
- 按钮使用紧凑分段控件形态，边框半径不超过 8px。
- 避免大段说明文案、装饰性卡片和与游戏无关的视觉元素。

### 5.5 可访问性与响应式

- 所有模式与难度按钮使用真实 `button`，提供明确文本。
- 当前模式与当前 AI 难度使用 `aria-pressed` 表达选中状态。
- 棋盘尺寸使用 `clamp()` 或响应式变量，保证 15 列不会溢出屏幕。
- 小屏下顶部工具条换行居中，状态区不遮挡棋盘。
- 减少字距和过大标题，避免中文在窄屏里显得松散。

## 6. 组件设计

### 6.1 `Game`

`Game` 继续作为页面状态协调组件，但移除 `gameStarted` 状态。它负责：

- 初始化游戏状态。
- 处理模式切换。
- 处理玩家落子。
- 触发 AI 落子。
- 渲染整体仪表盘布局。

### 6.2 `ModeSelect`

`ModeSelect` 从全屏入口页改为紧凑模式工具条。它负责：

- 展示“双人 / AI 对战”模式按钮，以及“简单 / 中等 / 困难”AI 难度按钮。
- 接收当前 `mode` 与 `aiDifficulty`。
- 对当前模式按钮和当前难度按钮加选中状态。
- 点击按钮后调用 `onSelect`。

### 6.3 `Board`

`Board` 保持现有职责：

- 渲染 15 x 15 棋盘。
- 标记最后落子。
- 标记胜利连线。
- 将点击坐标交给上层。

### 6.4 `Status`

`Status` 保持独立组件，继续根据 `GameState` 输出状态文案。样式更新为仪表盘底部状态条。

## 7. 数据流

```text
Game
 ├─ ModeSelect(current settings, onSelect)
 ├─ Board(board, lastMove, winningCells, onCellClick)
 └─ Status(gameState)
```

模式切换流程：

```text
点击模式或难度按钮
 → Game.handleModeSelect(mode, aiDifficulty)
 → dispatch({ type: 'SET_MODE', mode, aiDifficulty })
 → reducer 重置棋盘并应用新设置
 → UI 更新当前模式与空棋盘
```

落子流程与 AI 流程保持现有实现。

## 8. 测试策略

增加面向用户行为的组件测试：

- 初始渲染时棋盘、模式按钮和 AI 难度按钮同时出现。
- 默认模式为双人，默认 AI 难度为中等。
- 点击 AI 对战后，当前模式显示为人机中等，并且棋盘仍在页面上。
- 点击困难后，当前模式显示为人机困难，并且棋盘仍在页面上。
- 进行落子后切换模式会重置棋盘。

保留现有游戏逻辑测试，确保 UI 改造不影响胜负判断和 AI 行为。

## 9. 验收标准

- [ ] 打开应用即可看到标题、模式按钮、状态和棋盘。
- [ ] 不再出现独立全屏模式选择页。
- [ ] 当前模式和 AI 难度有清楚的选中态。
- [ ] 切换模式或 AI 难度会开始新局并更新模式标签。
- [ ] 棋盘在桌面端居中且是首屏主角。
- [ ] 棋盘在移动端不横向溢出。
- [ ] 状态、AI 思考、胜利提示和重新开始按钮行为正常。

- [ ] `npm run build` 通过。
